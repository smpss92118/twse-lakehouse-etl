01全貌：分層與寫入流程

資料分四層。每一層有明確的責任，壞掉時知道從哪一層重建。

Bronze 原始層

證交所回應原樣存檔，附 sha256 與抓取時間。只增不改。

bronze/<report>/trade_date=D/
Staging 暫存層

清洗後的 parquet，型別正確。它是「被稽核的對象」，不對外。

staging/<report>/trade_date=D/
Silver 正式層

三張 Iceberg 表：行情、法人、公司行動。稽核全過才寫入。

daily_quotes 等
Gold 合併層

一檔一列的合併表，策略團隊只看這張。

daily_market_wide

Write-Audit-Publish（先稽核再發布）

題目的順序是「寫入 Iceberg → 產出合併表 → 筆數檢查」。我改成先把資料寫到 staging（Write），在 staging 上跑完全部稽核（Audit），全部通過才寫進 Iceberg（Publish）。差別在於：檢查失敗時，正式表完全沒被碰過，不需要 rollback，策略團隊也不會在中間讀到壞資料。寫入後仍有一次對帳，確認實際 commit 進去的筆數；對不上就自動撤銷這次寫入（Gold 先、Silver 後），再失敗告警。

check_trading_day ─> wait_for_reports ─> route ─┬─> extract_{quotes,institutional,corporate_actions}
                                                │     ─> stage_* ─> audit ─> publish_silver ─> build_gold ─> reconcile（對不上 → 撤銷本次寫入）
                                                └─> check_unscheduled_closure（兩份都 0 筆 → 問 MI_5MINS）

每次執行最後寫一份 manifest（執行收據）：用了哪些 snapshot id、各表筆數、每一項檢查的結果。策略團隊引用資料時只要引用 snapshot id，就能精確重現。

為什麼多抓公司行動表（TWT49U、TWTAUU、TWTCAU）題目只要兩張表，但「昨收 − 漲跌 = 今收」這條最強的檢查，遇到除權息、減資、分割都會失效（漲跌改以開盤競價基準計算）；策略團隊算報酬也需要調整因子。所以留下公司行動，但只用證交所公布的參考價，不另外重算、不接第三方（見 07）。

02Airflow DAG 設計

對應題目 Q1。程式在 dags/twse_daily_etl.py，業務邏輯全部在 src/twse_etl/，DAG 只負責編排。

Task 怎麼切

切分原則是「一個 task 做一件可以單獨重跑的事」，而且失敗類型不同的步驟要分開，才能給不同的重試策略：

  • 判斷交易日用 @task.short_circuit：回傳 False 時下游全部 skipped，整個 run 是綠燈。題目要求「休市日主動略過，不是失敗」就靠這個。
  • 等資料用 sensor；分流用 @task.branch：資料到了走擷取，19:00 還沒到就走「查是否臨時休市」。
  • 擷取三張表各自一個 task，平行執行，網路錯誤各自重試。
  • 清洗、稽核、寫入、合併、對帳各自一個 task。task 之間只傳檔案位置、筆數、版本號這類小東西，資料本身不經過 XCom（避免把 metadata DB 塞爆）。

排程設定

設定值理由
timetableCronTriggerTimetable("30 15 * * 1-5", Asia/Taipei)15:30 觸發、處理的就是當天。舊的 data-interval 語意會在「下一個區間」才跑，容易讓人搞錯日期。
catchupFalse補資料用明確的 backfill 指令，不讓排程器自動補一堆舊日期。
max_active_runs1價格連續性檢查要讀「前一個交易日」的 Silver，所以日子必須照順序寫入。
dagrun_timeout8 小時只允許一個 run 同時跑，卡住的 run 會擋住隔天；先讓它失敗並告警（PR #1 加的）。
on_failure_callbacktask 層＋DAG 層task 重試用盡會告警；整個 run 逾時這種 task 不會回報的失敗，由 DAG 層告警。
手動指定日期{"trade_date": "2026-10-29"}補跑、重抓修正資料都用同一個 DAG，不另寫腳本。

交易日曆：三道關

  1. 排程只排週一到五（cron 的 1-5）。
  2. 官方開休市表（證交所 holidaySchedule）。實作時發現這張表裡也列了交易日，例如「國曆新年開始交易日」「農曆春節前最後交易日」，整張當休市表會漏跑，所以解析時要排除這些列（trading_calendar.py，有測試）。
  3. 臨時休市：颱風假永遠不會出現在官方表上。只能從「該有資料卻沒有」反推，再問證交所自己的盤中統計 MI_5MINS 確認（見 08）。

資料延遲：怎麼等、何時放棄

  • sensor 每 600 秒檢查一次，使用 mode="reschedule"：兩次檢查之間釋放 worker slot，不會佔著資源等好幾個小時。
  • 「資料到了」的定義不是「API 有回應」，而是 stat == OK、日期等於要求的那天、筆數達到下限（行情 ≥ 900、法人 ≥ 500）。這防止把空表或只發布一半的資料寫進去。
  • 17:00 起每次檢查都告警（兩張表正常約 16:30 前發布）；19:00 cutoff 放棄等待：只出了一份，代表市場有開、只是晚，直接失敗告警；兩份都 0 筆，才去查是否臨時休市。

重試與告警

步驟重試為什麼
extract_*3 次，指數退避，從 2 分鐘起網路錯誤、證交所暫時限流，等一下通常會好。
其他預設2 次，間隔 5 分鐘暫時性錯誤（例如 catalog 鎖）。
audit、reconcile、check_unscheduled_closure0 次資料錯了，重跑一百次結果都一樣。
資料類錯誤（稽核失敗、欄位漂移、確認缺資料）轉成 AirflowFailException，直接跳過剩餘重試立刻告警交給人處理，不浪費時間、不重複打證交所。

告警目前是 ALERT <event> {json} 的 log 行，集中在 twse_etl/alerts.py 的一個函式，換成 Slack 或 SNS 只改這一處。

同類工具比較

03擷取與清洗

題目要求「欄位名稱統一為英文，日期、數值型別正確，千分位與正負號符號要處理乾淨」。程式在 sources.py、transform.py、contracts.py。

資料源

報表內容備註
MI_INDEX（type=ALLBUT0999）每日收盤行情，約 1,390 檔含 ETF、特別股、ETN；不含權證、牛熊證
T86（ALLBUT0999）三大法人買賣超，約 1,340 檔只列當天有法人交易的股票，所以永遠比行情少

TWTCAUETF 分割／反分割恢復買賣的前收與參考價同上
holidaySchedule官方開休市表交易日判斷用

每次請求間隔 3 秒，避免被證交所封鎖。測試用的 fixtures/ 是證交所原始回應的逐位元組錄製，CI 不連網；被限流時設 TWSE_SOURCE=fixture 就能離線跑完整流程。題目允許「用自己下載的檔案模擬」，README 有說明。

欄位漂移（schema drift）

證交所改欄位名或少欄位時，SchemaDriftError 讓這天直接失敗（不重試，要人看）。多出新欄位時只告警，照常處理既有欄位。這樣「證交所悄悄改格式」不會變成「某欄安靜地全變 null」。

04資料品質把關

寫入前 24 項檢查（22 項擋寫入、2 項只告警），寫入後 4 項對帳，對不上就自動撤銷這次寫入。測試用真實的 10-29 資料全過，再逐一注入 25 種壞資料，每種都要讓對應的檢查失敗。

寫入前 24 項

最強的一條：價格連續性

每一檔都要滿足 今日收盤 − 有號漲跌 = 前一交易日收盤。它抓得到「筆數對、價格錯」的問題，例如欄位錯位、小數點位移、漲跌號解析錯，這些筆數檢查完全抓不到。真實資料每天約 1,360 檔參與檢查，0 筆不符。

例外處理：

  • X（不比價）：證交所自己說不可比，排除。
  • 除權息、減資、分割後：漲跌的基準是「開盤競價基準」，不是昨收，改用事件表的 open_ref_price。0050 在 2025-06-18 以 1 拆 4 恢復交易，47.57 − 0.41 = 47.16，正是參考價；停牌期間沒有昨收，靠事件表才檢查得到。
  • 颱風日的除權息：2026-10-23 颱風休市，但 TWT49U 仍列出當天除息的 2028、6931，在下一個交易日 10-27 生效，而且行情不標 X。只看「當天」的事件會誤報，所以事件抓「前一個交易日之後到今天」的區間。這是用真實資料才發現的。
  • 新上市、前一天沒收盤價的股票自然排除（沒有比較基準）。

門檻怎麼定

900／500／85% 是「底線」，不是預期值。正常日行情約 1,390 檔、法人約 1,340 檔、涵蓋率 96–97%。底線設低一些，目的是抓「只發布一半」這種大問題，又不會因為正常波動誤擋。生產環境應改成依歷史分布設定，例如「低於前 20 個交易日中位數的 90%」。

擋與不擋

只告警的兩項都在公司行動這個「加值欄位」上：對不上時照證交所公布值入庫並告警，不讓它擋住策略團隊明天要用的 1,390 檔行情與法人資料。擋下來會讓整天的資料延遲，而每天都誤擋的檢查會讓人開始忽略告警（alert fatigue）。因子超出範圍則是確定的解析錯誤，所以擋（見 07）。

寫入後 4 項對帳，不過就撤銷

  • Silver 行情筆數 = staging 筆數；Silver 法人筆數 = staging 筆數。
  • Gold 筆數 = 行情筆數；Gold 有法人資料的列數 = 法人筆數。

這是異常情境二（合併表 800 檔、行情 1,000 多檔、DAG 全綠）的防線，一共三道：寫入前的「涵蓋率 ≥ 85%」、寫入後的「Gold = 行情筆數」，以及對帳失敗時的自動撤銷（iceberg_io.undo_run）：

  • 這次 run 寫過的每張表，退回 run 之前的 snapshot，Gold 先、Silver 後，讀的人停在上一個正確版本。
  • 如果這次是那張表的第一次寫入，沒有前一版可退，就刪掉這次寫的列。這個 delete 帶上 trade_date 和 content_sha256 = "undone"，修好後用同樣內容重跑時，才不會被冪等檢查當成「內容沒變」而跳過。
  • manifest 記下 undone（每張表怎麼退的），然後 task 失敗並告警。

測試：把 gold.build 截成 800 列 → DataQualityError（gold_rows_equal_quotes）→ 每張表回到原本的筆數（首次載入則回到空表）；修好後重跑 → 1,388／1,388。

05Iceberg 與版本

對應題目 Q2 與全部五個版本示範。程式在 iceberg_io.py、scripts/demo_versioning.py。

Iceberg 是什麼：一棵 metadata 樹

catalog（SQLite / Postgres / Glue）
  └─ 指向目前的 metadata.json        ← commit 就是「原子地換掉這個指標」
       └─ snapshots[]                  ← 每次寫入一個；有 id、時間、summary
            └─ manifest list
                 └─ manifest files     ← 記錄每個資料檔的 partition 與統計
                      └─ data files（parquet）

寫入時先寫好新的資料檔和 metadata，最後在 catalog 用 compare-and-swap 把指標換到新的 metadata.json。換成功才算 commit；同時有人寫入就失敗重試（樂觀並行控制）。讀的人永遠只看到換指標前或換指標後，不會看到一半。

為什麼不直接放 parquet

需求單純 parquet 資料夾Iceberg
「上週二早上這張表長什麼樣」做不到，檔案被覆蓋就沒了time travel 到任一 snapshot
重寫某一天時，讀的人會不會讀到一半會（先刪後寫的空窗）不會，原子 commit
寫錯了退回要自己備份rollback，只改 metadata
中途加欄位新舊檔案欄位不一，讀取端要處理欄位用 ID 追蹤，舊檔讀出 null
每次寫入是誰、什麼來源沒有snapshot summary 存 run_id、trade_date、內容指紋

Partition：現在按日，回補多年歷史後改按年＋compaction

  • 現在是 identity(trade_date)。查詢幾乎都按日期篩；證交所的修正也是以「一天」為單位。修正某天就是原子地換掉那一天的檔案，snapshot 上的增刪一目了然（刪 1,388、加 1,388），也正好是題目說的「overwrite partition」，不需要額外套件。
  • 不用 stock_id 切：約 1,400 檔 × 每天，會變成幾十萬個小 partition，而且查詢通常是「某天全部股票」。
  • Iceberg 是 hidden partitioning：查詢只要寫 WHERE trade_date = ...，不用知道資料夾怎麼切。

代價是小檔：每張表一天只有約 72 KB。用 scripts/bench_partitions.py 實測 500 個交易日（每天 1,390 檔，照 pipeline 的寫法每天一次 overwrite commit，本機 SSD）：

  • 檔案數由 commit 次數決定，不是分區粒度。只改按年、不 compaction，檔案一樣多，單日查詢反而變慢。
  • 效益來自 compaction；按年分區的作用是讓 compaction 能把一年合成一個檔，因為 compaction 不跨分區。
  • 兩種寫法的 commit 延遲都隨 commit 數上升（每天多一個 manifest），所以 manifest 合併與 snapshot 過期本來就該排程。

計畫：歷史回補到多年時，partition evolution 改 year(trade_date)（只改 metadata，舊檔不重寫，新舊 layout 共存）；每週 compaction（Trino ALTER TABLE … EXECUTE optimize，PyIceberg 0.12 還沒有 compaction）；snapshot 過期；被訊號引用的 snapshot 先打 Iceberg tag，過期後仍答得出「上週訊號用哪一版」。用 year() 寫入需要 pyiceberg-core（Rust），所以 benchmark 用 uv run --with "pyiceberg[pyiceberg-core]" 跑，不加進 pipeline 的依賴。

重抓同一天：不重複，又留兩版

寫入一律是 overwrite(overwrite_filter = trade_date == D)：把那一天整個換掉。PyIceberg 會在同一次 metadata commit裡產生兩個 snapshot：delete（刪掉舊的那天）和 append（寫入新的那天），兩個都帶同一個 run_id。

  • 不重複：同一天永遠只有一份。
  • 兩版都在：修正前的內容留在前一個 snapshot，用 time travel 查得到。
  • 冪等看內容，不看來源 bytes：寫入前算「內容指紋」，也就是排除 run_id、寫入時間這些每次都不同的欄位後，資料排序再取 sha256，記在 snapshot summary。和目前版本相同就跳過，所以重跑不會製造雜訊版本，snapshot 清單裡的每個版本都代表「資料真的變了」。反過來，修好 parser 後重跑，證交所 bytes 沒變但內容變了，照樣寫新版。早期版本比對的是來源 bytes，這個情況會被略過；獨立 review 抓到後改掉，並寫成測試。

為什麼用 overwrite partition，不用 MERGE

做法適合這題
overwrite partition（採用）來源每次給「一整天的完整快照」證交所修正是重新發布整天，整天替換最簡單、最不會錯
MERGE INTO（upsert）來源只給「變動的列」（例如 CDC）還要處理「某檔被刪除」的情況；PyIceberg 0.12 也沒有完整 MERGE

延伸：Iceberg 的列層級更新有 copy-on-write（改寫整個資料檔，讀快寫慢）和 merge-on-read（寫 delete file，讀時合併，寫快讀慢）兩種。這題用整個 partition 替換，等於 copy-on-write 的極端情況，讀取端完全沒有額外成本。

維護：snapshot 不能無限長大

每次寫入都留檔案，久了要清：expire snapshots（刪掉過期版本）、compaction（合併小檔）、remove orphan files（清掉沒被引用的檔）。生產環境通常用 Trino（ALTER TABLE ... EXECUTE expire_snapshots / optimize）或 Spark 的維護程序排程執行。

06合併表

題目要求「兩張表用股票代碼與日期 join，產出每日個股行情＋法人買賣超的合併表」。程式在 gold.py。

LEFT JOIN，從行情出發

T86 只列當天有法人交易的股票。10-29 行情 1,388 檔、法人 1,340 檔，inner join 會安靜地少掉 48 檔。所以：

  • 以行情為主做 LEFT JOIN，合併表筆數永遠等於行情筆數。
  • 沒有法人資料的股票，法人欄位填 0，並用 institutional_reported = false 區分「真的零交易」和「資料缺漏」。
  • 對帳檢查：Gold 筆數 = 行情筆數；Gold 中 institutional_reported = true 的列數 = 法人筆數。

欄位

交易日、代號、名稱、OHLC、漲跌號與漲跌、成交股數、成交金額；外資、外資自營商、投信、自營商、三大法人合計的買賣超；institutional_reported、is_ex_event（除權息事件，例如 10-27 的 2028、6931）、adj_factor（當天所有事件的因子相乘）、corporate_action（當天生效的事件類型，例如 10-27 的 1516、6142 是 capital_reduction）；以及血緣欄位：quotes_snapshot_id、institutional_snapshot_id、run_id、built_at。

Gold 的冪等

Gold 和 Silver 用同一套內容指紋：每次都重建，但內容和目前版本一樣就不寫。Silver 被修正（例如證交所重新發布某天），Gold 內容跟著變，就留下一個新版本；它讀的 Silver snapshot id 也記在 Gold 的欄位裡。

替代做法：用 view

也可以在 Trino 建 view，查詢時才 join。好處是不用存第二份資料；壞處是 view 沒有自己的版本歷史，「上週那一版合併表」要靠兩張底表的 time travel 拼回來。策略團隊要的是能引用版本的一張表，所以實體化成 Gold 表。

07還原權值（調整價）

除權息、減資、分割會讓價格跳一格，未調整的序列會把它當成真的漲跌。做法是直接採用證交所公布的參考價，算出每日調整因子並檢查「我們讀對了」；Gold 保存原始價和因子，還原價在查詢時才算。程式在 corporate_actions.py、adjust.py。

題目沒要求，為什麼要做

  • 擋寫入的連續性檢查需要它：事件生效日的漲跌是相對「開盤競價基準」，不是昨收。10-23 颱風日除息的 2028、6931 在 10-27 生效，沒有事件表，這兩檔會讓連續性檢查失敗，整天擋下。
  • 策略團隊算報酬需要因子：沒有因子，除權息日的跳空會被當成真的虧損。

範圍刻意收窄：只用證交所公布的值，不另抓明細頁重算，也不接第三方資料（理由見 13 面試問答 Q46、Q48）。

證交所報表事件生效日用到的欄位
TWT49U除權、除息（含現金增資除權）除權息交易日除權息前收盤價、除權息參考價、權值+息值、開盤競價基準
TWTAUU減資（彌補虧損、退還股款）恢復買賣日停止買賣前收盤價格、恢復買賣參考價、開盤競價基準

adj_factor = 參考價 ÷ 事件前收盤，同一天有多個事件就相乘。三張報表都抓「前一個交易日之後到今天」的區間，每一頁原樣存進 Bronze，所以「當時拿到的數字」也有版本可查。

檢查：驗「我們讀對了」，不驗「證交所算對了」

參考價是證交所自己的定義，市場就照它交易。會出錯的是我們這一端：讀錯欄、解析錯數字。

檢查內容不過時
ca_adj_factor_range除權息 (0, 1]；減資與分割 (0, 100]。超出就是解析錯誤擋
quotes_price_continuity非 X 日：收盤 − 漲跌 = 開盤競價基準。0050 在 2025-06-18 以 1 拆 4 恢復交易，47.57 − 0.41 = 47.16，正是 TWTCAU 的參考價：交易所自己的價格序列確認了事件擋

同一列三個欄位對得上，就代表沒有一個是從錯的欄位讀來的。證交所是「捨去」到分，不是四捨五入：2330（2026-03-17）那一列是 1,845.00 − 6.000035 = 1,838.999965，公布 1,838.99。所以條件是 0 ≤ 差 < 0.01，用 decimal 精確計算；「誤差一檔」在千元以上是 5 元，太鬆。錄到的 94 筆 TWT49U 事件全部成立，參考價差 1 分也會被抓到，都寫成測試。

前復權與後復權

方法怎麼算適合
前復權（backward，預設）最後一天保持原價，之前的價格乘上之後所有因子看圖、算到今天為止的報酬
後復權（forward）第一天保持原價，之後的價格除以之前所有因子回測（point-in-time）：新的一天加進來時，舊價格不會變

兩種算出來的報酬率完全一樣，差別只在價格水準。0050 分割：未調整的序列顯示 −74.8%；兩種還原後都是 +0.87%，等於證交所自己的 0.41 ÷ 47.16。

make demo-adjusted STOCK=2762 START=2026-10-28 END=2026-10-30 METHOD=forward  # 後復權

-- Trino：前復權收盤
SELECT trade_date, close,
  round(close * coalesce(exp(sum(ln(adj_factor)) OVER (PARTITION BY stock_id ORDER BY trade_date DESC
    ROWS BETWEEN UNBOUNDED PRECEDING AND 1 PRECEDING)), 1), 4) AS close_adj
FROM iceberg.twse.daily_market_wide WHERE stock_id = '2762' ORDER BY trade_date

為什麼存因子，不存調整後的價格

做法優勢劣勢
存原始價＋每日因子，查詢時算（採用）歷史不改寫；每個 snapshot 都能算出當時的還原價；因子錯了只改一筆查詢時多一步累乘
直接存調整後價格讀取最簡單每次除權息都要改寫整段歷史，舊版本全部和今天對不上，「上週訊號用哪一版」答不出來
買現成的還原價（第三方資料商）不用自己算黑盒，資料源算錯時無從得知；多一個外部依賴，而參考價本來就是證交所定義的
還沒涵蓋的面額變更（例如 10 元改 1 元）在證交所網站找不到 JSON 資料源，目前沒有調整因子。上櫃股票不在範圍內。

  • 之後的日子：記錄過的休市日，下一個交易日的「前一交易日已載入」檢查會跳過它，不會要求先補一個沒開盤的日子。

  • 人工補記（例如事後確認）：python -m twse_etl.pipeline record-closure --date 2026-10-23 --reason "颱風"。

為什麼要等 cutoff，而且兩份都 0 筆

如果只靠單一來源，它暫時異常回「沒資料」時，交易日就會被判成休市、靜默略過。要求兩個獨立條件同時成立（行情、法人都沒有任何一列，而且交易所的盤中統計也說沒有），任何一邊答錯，結果只會是「多告警一次」，不會是「少一天資料」。

09CI/CD 與搬上 AWS

對應題目 Q3 與實作 3。設定在 .github/workflows/、scripts/deploy_dags.sh。

CI：每次 push 和 PR 都跑兩個 job

  • Cleaning logic unit tests：uv sync --locked 安裝鎖定版本 → ruff lint＋格式檢查 → pytest。測試包含清洗、交易日與臨時休市、稽核（25 種故障注入）、對帳失敗撤銷、還原權值（94 筆真實除權息），以及用錄好的真實證交所資料跑的端到端流程，共 67 個，不連網，約 4 秒。
  • DAG imports and has no cycles：先 build 正式的 Airflow image，在 image 裡跑 DagBag（2 個測試）：沒有 import error、沒有循環、task 順序符合規格。在正式 image 裡測，才能抓到「本機有裝、production 沒裝」的套件問題。

CD：main 的 CI 成功後自動觸發

CD 用 workflow_run 監聽 CI，條件是：CI 成功、由 push 觸發、分支是 main、而且來自本 repo（或手動 workflow_dispatch）。只看「分支叫 main」不夠：fork 也可以有一個叫 main 的分支送 PR，這個漏洞在獨立 review 時被找到，PR #3 修正。然後執行 deploy_dags.sh：

  1. 拒絕空的 dags/：沒有任何 DAG 檔就中止。這是針對異常情境三（merge 後 DAG 全部消失）的防線，因為下一步的 rsync --delete 會把目標清空。
  2. 所有要部署的 Python 檔先 py_compile。
  3. 在暫存資料夾組好 bundle：dags＋twse_etl 套件＋.airflowignore（讓 Airflow 不把函式庫當 DAG 解析）＋DEPLOYED_VERSION（commit sha）。
  4. rsync --delete 鏡像到目標資料夾（刪掉的 DAG 也會跟著刪）。
  5. 每版留一個 tarball，回滾就是解壓上一版。

GitHub 上把 bundle 上傳成 artifact airflow-dags-<sha>。本機用 make deploy-from-ci 把那一包裝進 Airflow 掛載的資料夾。GitHub 的雲端 runner 連不到本機，所以本機最後一步是一行指令；題目也說「CD 在本機模擬即可，例如把 dags/ 打包成 artifact」。

image 與程式分開：image 只裝第三方套件；DAG 和 twse_etl 透過掛載資料夾部署。改程式不用重 build image，部署只要幾秒。

11GPU 訓練與運算引擎

之後上 AWS 要用大量 GPU 跑 Transformer、GRU、boosting 和基因演算法因子挖掘。建議：Polars 為主（搭配它的 GPU 引擎），訓練直接吃 Arrow／GPU 記憶體；Trino 只當給人查的 SQL 層（AWS 上換 Athena）；Spark 等資料大到單機放不下再上；DuckDB 當互動分析的輔助。

先分清楚：四個工具不在同一層

工具是什麼GPU在這套架構的位置
Polars（建議主力）單機 DataFrame 引擎（Rust、Arrow）有：GPU 引擎（NVIDIA cuDF，collect(engine="gpu")），同一份程式碼特徵工程；pipeline 已經在用

為什麼是 Polars

  • 資料量其實不大：日頻 1,400 檔 × 250 天 × 20 年約 700 萬列，一台機器的記憶體就裝得下；分鐘線 10 年約 10 億列，單機 GPU 節點分批讀取也處理得了。分散式的協調成本在這個量級是純負擔。
  • 瓶頸在 GPU 訓練：訓練花的時間遠大於準備資料。Polars → Arrow → PyTorch／XGBoost 不經過 pandas，少一次複製；GPU 引擎讓 group_by、join、rolling 也在 GPU 上跑。
  • 同一套程式：清洗、稽核、還原價都已經用 Polars 寫，研究端沿用，就不會出現「研究和 production 算法不一樣」。
  • 版本可重現：PyIceberg 讀「某個 snapshot id」轉成 Polars，訓練資料就標註了版本，回測可以重現。

  • Iceberg 的大規模維護（compaction、重寫歷史）；不過 AWS 上 Athena 的 OPTIMIZE 和 Glue 的自動 compaction 多半就夠。
  • 代價是叢集維運、JVM 調校，以及比較慢的迭代速度。

13面試問答

題目說「現場會針對每個設計決策追問」。下面依主題整理可能的問題。先自己回答，再展開對照。每題有一段可以直接說的「建議回答」，和一段幫你理解背後原理的「講解」。

Airflow 與 DAG

Q1為什麼 task 這樣切？切更細或更粗會怎樣？

我用兩個原則切：一個 task 做一件可以單獨重跑的事；失敗類型不同的步驟要分開。擷取是網路問題，要重試；稽核是資料問題，不該重試，所以一定要拆開。切更粗，一個錯就要整段重跑，也看不出壞在哪；切更細，task 之間要傳更多中間狀態，排程開銷也變大。

Airflow 的重試、逾時、告警都是以 task 為單位設定的，所以「重試策略不同」是最實際的切分依據。task 之間只傳檔案位置和版本號，資料不走 XCom。

Q2交易日怎麼判斷？颱風假怎麼辦？

三道關。cron 只排週一到五；再查證交所的官方開休市表；颱風假不會出現在官方表上，所以 19:00 cutoff 時如果行情和法人都還是 0 筆，就問證交所的盤中統計 MI_5MINS。它明確回「沒有符合條件的資料」才當休市，原始回應存進 Bronze 當證據，run 綠燈；有盤中紀錄或任何其他回答，一律失敗告警。

官方表本身也有坑：裡面列了「開始交易日」「最後交易日」這種交易日，整張當休市表會漏跑。10/23 薔琵颱風是真實案例：MI_INDEX、T86 的回應和一般假日完全相同；MI_5MINS 在正常日 10/22 有 3,241 筆，10/23 和 2024-10-31 兩個颱風日都是「沒有資料」。

Q3資料晚發布怎麼等？什麼時候放棄？

sensor 每 10 分鐘檢查一次，用 reschedule 模式，等待期間不佔 worker。「資料到了」的定義是狀態 OK、日期正確、筆數達到下限，避免寫入空表或只發布一半的資料。17:00 起每次都告警，19:00 放棄等待，轉去判斷是不是臨時休市。

17:00 是因為兩張表正常 16:30 前會發布；19:00 留了兩個半小時的緩衝，同時離隔天開盤還很遠，有人能處理。這兩個時間應該和策略團隊對齊他們的 deadline。

Q4為什麼 sensor 用 reschedule，不用 poke 或 deferrable？

poke 會一直佔著 worker slot，等三小時就佔三小時。reschedule 每次檢查完就釋放 slot，一天一個 DAG 最划算。deferrable 在有大量 sensor 時更省資源，但要多跑 triggerer、寫 async 程式，這個規模不需要。

如果之後要等幾十個資料源，就值得改 deferrable。

Q5失敗要重試，為什麼有些 task 不重試？

重試只對暫時性錯誤有用。擷取遇到網路錯誤或限流，重試 3 次、指數退避。稽核失敗、欄位改名、確認缺資料，這些是資料本身的問題，重抓同一份資料結果一樣，所以轉成 AirflowFailException 直接失敗告警，不浪費時間、也不重複打證交所。

題目要求「重試用盡要告警」：task 層的 on_failure_callback 在重試用盡（或 AirflowFailException）時觸發。另外 DAG 層也有 callback，整個 run 逾時這種 task 不會回報的失敗也會告警。

Q6為什麼 max_active_runs=1？補一年資料會不會很慢？

價格連續性檢查要讀前一個交易日的 Silver，所以日子必須照順序寫入。一天大約 13 秒，加上對證交所每次請求間隔 3 秒，補一年約 250 個交易日，大概一小時內，可以接受。

副作用是卡住的 run 會擋住隔天，所以加了 8 小時的 dagrun_timeout（PR #1）。

Q7為什麼用 CronTriggerTimetable？logical date 是哪一天？

我要 15:30 觸發、處理的就是當天的資料。舊的 data-interval 語意是在區間結束時跑「上一個區間」，對每日收盤資料很容易搞錯日期。CronTriggerTimetable 的 logical date 就是觸發時間，所以排程的那天就是交易日。

手動指定日期時用 conf 的 trade_date，覆蓋排程日期。

Q819:00 之後證交所才發布，怎麼辦？

19:00 時如果只出了一份，代表市場有開、只是晚，直接失敗告警。兩份都還沒出，就問 MI_5MINS：那天有開盤，就會有盤中紀錄，所以一樣失敗告警，不寫入任何東西。值班的人確認資料出來後，用 trade_date 參數手動觸發一次就好，寫入是冪等的。

設計的底線是「不確定就不寫、一定告警」，而不是「盡量自動處理」。

Q9Airflow 3 的 Asset-driven scheduling 有用嗎？

有用，但用在 ETL 的出口，不是拿來拆內部。Gold 發布成功時可以發出一個以 trade_date 為 key 的 partitioned asset（Asset Partitions 在 Airflow 3.2 推出；3.3 的 RollupMapper 能等齊一週或一個月的 partition），因子和 ML 的 DAG 訂閱它，資料真的好了才跑，不用拿 cron 猜時間。每天這條 Write-Audit-Publish 鏈不拆：三張 Silver、跨表稽核和 Gold 是一個單位，拆成各自觸發的 asset，就會出現「行情新、法人舊」的中間狀態。

Asset 回答的是「下游什麼時候該跑」，WAP 回答的是「什麼時候可以發布」，兩件事分開設計。不要說成 Airflow 借鏡 Dagster：Airflow 的文件沒有這樣寫。

資料品質與清洗

Q10筆數檢查之外，你怎麼知道資料是「對的」？

最強的是跨日勾稽：今收減漲跌必須等於昨收。這條抓得到筆數對、價格錯的問題，例如欄位錯位、小數點位移、正負號解析錯。真實資料每天約 1,360 檔參與，0 筆不符。另外還有法人內部加總、跨表一致性，公司行動在同一列內勾稽前收、權值+息值和參考價。

筆數檢查只能保證「量」，連續性檢查才保證「值」。

Q11除權息、停牌、新上市，連續性檢查不會誤報嗎？

證交所標 X（不比價）的排除；除權息日改用除權息表的開盤競價基準；新上市和前一天沒收盤價的，沒有比較基準，自然不比。還有一個是用真實資料才發現的：颱風休市那天除息的股票，會在下一個交易日生效而且不標 X，所以除權息事件要抓「前一個交易日之後到今天」的區間。

10/23 颱風日除息的 2028、6931，在 10/27 用開盤競價基準計算漲跌。只看當天事件的話，這兩檔會被誤報。

Q12門檻 900、500、85% 怎麼來的？

這些是底線，不是預期值。正常日行情約 1,390 檔、法人 1,340 檔、涵蓋率 96–97%。底線的用途是抓「只發布一半」這種大問題，又不會因為正常波動誤擋。上線後我會改成依歷史分布的動態門檻，例如低於前 20 日中位數的 90% 才擋。

固定門檻在長期一定會過時，例如上市家數持續增加；動態門檻要配合足夠的歷史資料。

Q13為什麼價格用 Decimal，不用 float？

float 存不準十進位小數，例如 0.1 加 0.2 不等於 0.3。連續性檢查要求「完全相等」，用 float 會有誤差，只能改用容許誤差，等於放寬了檢查。Decimal(12,2) 剛好對應證交所兩位小數的報價。

股數、金額用 int64；本益比 0.00 表示「無」，存 null。

Q14證交所改欄位名稱怎麼辦？

缺少預期欄位時直接失敗，不重試，告警請人看；多出新欄位只告警，照常處理既有欄位。這樣格式變更不會變成「某一欄安靜地全變 null」。

對照表集中在 contracts.py，修正時只改一處，再用 fixture 補一個測試。

Q15為什麼不用 Great Expectations 這類工具？

這題的關鍵檢查是跨日連續性和跨表涵蓋率，這種業務規則在任何工具裡都要自己寫。自己寫的 Check 清單沒有額外依賴，每條都能單元測試，結果直接進 manifest。團隊變大、需要報表 UI 時，再遷移到 Great Expectations 或 Soda。

工具的價值在規則管理和報表；規則本身的正確性還是得靠對資料的理解。

Q16為什麼不用 Pandera，或 DuckDB 的 SQL 斷言？

檢查已經是宣告式的：每條是一個 Polars 表達式，回傳違規的列，不是一堆 if-else，結果直接寫進 manifest。Pandera 可以把單表契約標準化，例如型別、null、主鍵、OHLC 範圍，這部分換過去合理；但跨表涵蓋率、跨日連續性、公司行動這些規則，在 Pandera 裡還是要自訂。DuckDB 斷言則是為了檢查再引入第二個引擎，資料本來就在 Polars 裡。

選工具看它省掉哪一段；這題最有價值的規則，正好是工具給不了的那一段。

Iceberg 與版本

Q17為什麼用 Iceberg，不直接放 parquet？

三個 parquet 做不到的事：第一，每次寫入是一個 snapshot，能回答「上週二早上這張表長什麼樣」；第二，寫入是原子的，重寫某一天時，讀的人不會讀到一半；第三，能 rollback、能加欄位而不重寫舊資料。這三件剛好對應題目的需求：查當時內容、修正不重複、寫錯能回。

原理是 catalog 裡一個指向 metadata 檔的指標，commit 就是原子地把指標換到新的 metadata。

Q18Partition 為什麼按日？不會小檔嗎？

按日的好處是修正一天就是原子地換掉那一天的檔案，snapshot 上看得到刪 1,388、加 1,388，正好是題目說的 overwrite partition，也不用額外套件。小檔我量過：500 個交易日、每天一次 commit，按日是 500 個檔；只改按年、不 compaction，還是 500 個檔，單日查詢反而從 9.5 ms 變 150 ms。檔案數是 commit 次數決定的，不是分區粒度。效益來自 compaction：按年加 compaction 剩 2 個檔，讀全部從 531 ms 降到 10 ms。所以回補多年歷史後，用 partition evolution 改按年，加每週 compaction。

按年的意義是讓 compaction 能把一年合成一個檔（compaction 不跨分區）；partition evolution 只改 metadata，舊檔不重寫。按股票切會變成幾十萬個小 partition，而查詢通常是某天全部股票。完整數字在 05。

Q19重抓同一天，怎麼做到不重複又保留兩版？

寫入一律是「把那一天整個換掉」：overwrite 加上 trade_date 等於那天的條件。同一天永遠只有一份，所以不重複；修正前的內容留在上一個 snapshot，所以兩版都查得到。內容指紋（排除 run_id、時間等欄位後的 sha256）和目前版本一樣就跳過，重跑不會產生多餘版本；修好 parser 後重跑，內容變了就會寫新版。

PyIceberg 會在同一次 metadata commit 裡產生 delete 和 append 兩個 snapshot。現場示範 make demo-correct：改了 2330 的成交股數後，表裡仍是 1,388 檔、沒有重複，前後兩個 snapshot 各自查得到舊值和新值。

Q20為什麼用 overwrite partition，不用 MERGE？

證交所修正時是重新發布一整天，來源本來就是「整天的完整快照」，整天替換最簡單也最不容易錯。MERGE 適合來源只給變動列的情況，例如 CDC，而且還要處理「某檔被刪掉」的情況。

題目也寫「MERGE 或 overwrite partition」都可以。如果之後有逐筆更新的資料源，再引入 MERGE（例如用 Spark 或 Trino）。

Q21time travel 的「時間」是什麼時間？怎麼回答「上週算訊號用的是哪一版」？

是 commit 時間，不是交易日。最精確的做法是不靠時間：每次執行的 manifest 記下合併表的 snapshot id，策略團隊算訊號時引用這個 id，之後用它 time travel，就能拿到一模一樣的資料。用時間查，則是「那個時間點最新的一版」。

對回測特別重要：用修正後的資料回測，等於用了當時拿不到的資訊（look-ahead）。

Q22rollback 之後，原本的資料去哪了？

還在。rollback 只是把 current 指標指回舊的 snapshot，被退掉的 snapshot 和資料檔都沒刪，必要時可以再指回去。真正刪除要等 expire snapshots 和清理孤兒檔案。

所以 rollback 是幾乎零成本的止血動作，這也是異常處理時「先退回上一版」能很快做到的原因。

Q23snapshot 會無限長大嗎？清掉不就查不到上週版本？

要定期 expire 舊 snapshot、合併小檔、清孤兒檔。這和「查上週版本」確實有衝突，所以保留期要跟策略團隊對齊，例如至少 90 天；被訊號引用過的版本打 tag，tag 有自己的保留期，不會被一般清理刪掉。目前專案還沒設保留政策，這是上線前要補的。

維護通常排程用 Trino 的 ALTER TABLE … EXECUTE expire_snapshots / optimize 或 Spark 的維護程序執行。

Q24兩個人同時寫同一張表會怎樣？

Iceberg 用樂觀並行控制：每個 writer 寫好自己的檔案，commit 時在 catalog 做 compare-and-swap，後到的發現指標變了就失敗重試。SQLite catalog 同時只能一個 writer，所以我讓三張 Silver 表由同一個 task 依序寫入。多人或多個 pipeline 時換 Postgres 或 Glue，這個我在大資料配置驗證過了。

寫入不同 partition 的兩個 commit 通常能自動重新套用，衝突機率低。

Q25Iceberg、Delta Lake、Hudi 怎麼選？

Iceberg 引擎中立，Spark、Trino、Flink、DuckDB、Athena、Snowflake 都能讀寫，而且有 PyIceberg，不用 JVM 就能在 Airflow 裡寫，這是我選它的主因。Delta Lake 在 Databricks 生態最完整；Hudi 強在高頻 upsert 和增量讀取，適合串流 CDC。這題每天批次寫一次，Iceberg 最合適。

Iceberg 的 hidden partitioning 和 partition evolution 也讓「之後改切法」沒有成本。

Q26schema evolution 為什麼舊資料還能讀？改欄位名呢？

Iceberg 用欄位 ID 而不是欄位名稱追蹤欄位。加欄位時，舊的資料檔沒有這個 ID，讀出來就是 null，不用重寫。改名也只改 metadata，因為底層認的是 ID。如果是用名稱對應的 parquet，改名就等於舊資料那欄消失。

示範 make demo-evolve：加欄位後，舊 snapshot 照樣能查，新欄位在舊資料上是 null。

CI/CD 與部署

Q27CI 檢查什麼？為什麼 DAG 要在正式 image 裡測？

兩個 job：一個跑清洗與稽核的測試，用錄好的真實證交所回應加上 25 種故意弄壞的版本，共 67 個，不連網，約 4 秒；另一個先 build 正式的 Airflow image，在裡面確認 DAG 能 import、沒有循環。在正式 image 裡測，才能抓到「我電腦有裝、production 沒裝」的套件問題和 Airflow 版本差異。

測試用 fixture 而不是真的打 API，CI 才會穩定，不會因為證交所限流而變紅燈。

Q28CD 怎麼把 DAG 送到 Airflow？

本 repo 的 main 有 push、CI 成功後，自動觸發 CD；fork 送來的 PR 不會觸發。部署腳本先檢查 dags/ 不是空的、所有檔案能編譯，再把 DAG 和程式套件組成一包、寫上版本號，同步到 Airflow 掛載的資料夾，並保留每一版的壓縮檔方便回滾。GitHub 上這一包存成 artifact；本機用一行指令裝進去。上 AWS 時同一包用 OIDC 同步到 MWAA 的 S3。

image 只裝第三方套件，程式透過掛載資料夾部署，所以改程式不用重 build image。

Q29為什麼 CD 不直接推到你的電腦？能不能全自動？

GitHub 的雲端 runner 連不到我的電腦。要全自動有三種做法：在本機跑 self-hosted runner，但這是公開 repo，別人的 PR 可能在我機器上執行程式，不安全；本機定時拉 CI 的產物；或直接上雲，merge 後自動同步到 MWAA。題目也說 CD 在本機模擬即可。

Airflow 3 的 GitDagBundle 也能讓 Airflow 直接從 Git 拉 DAG，但會少掉「部署前檢查」那一道關。

Q30搬到 AWS，哪些要改、哪些不用？

要改的都是設定：catalog 換 Glue、資料路徑換 S3，都是環境變數；requirements 加 Glue 和 S3 的套件；CD 開啟 AWS 那個 job；告警改送 SNS 或 Slack。清洗、稽核、Iceberg 讀寫和 DAG 程式碼都不用改。這不只是理論：我把 catalog 換成 Postgres、資料換成 S3 相容儲存，pipeline 程式完全沒改就跑通，還用 Trino 查到了同樣的版本。

關鍵設計是 get_catalog 是唯一知道 catalog 位置的函式，storage.py 用 pyarrow FileSystem，本機路徑和 s3:// 是同一套呼叫。

Q31部署了壞版本，怎麼回滾？

每一版都有壓縮檔，解壓上一版到掛載資料夾就回去了，Airflow 自動重新載入；或者 revert 那個 commit，走一次正常的 CI/CD。資料面如果已經被壞版本寫錯，用 Iceberg rollback 退回寫入前的 snapshot。

程式回滾和資料回滾是兩件事，兩件都要能做到。

Q32金鑰怎麼管？

repo 裡沒有任何金鑰。本機的 secret 在 .env 裡，由 make 在每台機器隨機產生、gitignore 擋住。上 AWS 用 GitHub OIDC 換臨時憑證，不存長期 key。pipeline 本身不需要任何第三方 API key：資料源是證交所公開 API，臨時休市也是問證交所。

大資料配置裡的 S3 key 是只在本機容器之間有效的固定值，object store 不對外開 port，不是真的憑證。

異常處理與營運

Q33為什麼選情境二？

因為它最危險：沒有錯誤訊息、流程全綠，壞資料安靜地進到策略。情境一和三至少會有人發現，情境二要等策略出問題才會被發現。而且我用真實資料就重現了它：10/29 行情 1,388 檔、法人 1,340 檔，inner join 會少 48 檔。現在對帳失敗還會自動撤銷這次寫入，讀的人不會看到少了列的合併表。

核心觀念：「成功」要包含資料檢查，不只是程式沒報錯。

Q34情境一（颱風日寫入空 snapshot），你的設計會發生嗎？發生了怎麼處理？

不會發生。「資料到了」要求筆數達到下限，空表根本不會進入擷取；寫入前也有筆數檢查；颱風日要兩份報表都 0 筆、MI_5MINS 也明確沒有盤中資料，才記成休市並略過，什麼都不寫。萬一真的發生：先 rollback 到前一個 snapshot、重建合併表、通知策略團隊；用 manifest 找出哪個 run 寫的；最後補上防線。

預防的設計就是三道交易日關卡加上完整性定義。

Q35情境三（merge 後 DAG 全消失），你的設計會怎樣？

部署腳本會拒絕空的 dags/，而且 CI 要求 DAG 能 import，所以「整包變空」或「DAG 壞掉」都到不了 Airflow。如果還是發生，就解壓上一版壓縮檔，馬上恢復；同時回答策略團隊：資料寫在 Iceberg，已經寫入的都還在，今天的 run 恢復後會照常補上。

rsync --delete 的特性是「目標會變得跟來源一樣」，所以空來源會清空目標，這正是需要防呆的原因。

Q36寫入後對帳失敗，資料不是已經進去了嗎？

commit 了，但不會留著。reconcile 發現筆數對不上，會在 task 失敗之前自動撤銷這次 run：每張表退回 run 之前的 snapshot，Gold 先、Silver 後；如果是第一次載入，就刪掉這次寫的列。manifest 記下 undone，然後失敗告警。測試把合併表截成 800 列：檢查擋下，每張表回到原本筆數；修好重跑是 1,388／1,388。剩下的限制是 commit 到撤銷之間讀得到；要完全消除，用 Iceberg branch：先寫 audit 分支，檢查過才 fast-forward 到 main。

第一次載入的刪除會標上 content_sha256 = "undone"，否則修好後用同樣內容重跑，會被冪等檢查當成「內容沒變」而跳過。

Q37三張 Silver 表的寫入是原子的嗎？

每張表各自的 commit 是原子的，三張之間不是：Iceberg 本身沒有跨表交易。中途失敗會出現行情是新的、法人還是舊的。我的處理是合併表只在三張都寫完後才建；重跑是冪等的，會把缺的補齊；manifest 記錄每張表的版本，策略只讀合併表。需要真正跨表原子性時，可以用 Nessie 這類支援多表交易的 catalog。

實務上，下游只讀一個「經過確認的出口」（Gold＋manifest），就能避開大部分跨表不一致的問題。

Q38臨時休市判斷錯了會怎樣？

要判成休市，三件事必須同時成立：已過 19:00 cutoff、行情和法人都是 0 筆、MI_5MINS 明確回「沒有資料」。其中任何一個來源答錯，結果只會是失敗並多告警一次，不會把交易日靜默略過。判成休市時，closures 檔記著 Bronze 裡原始回應的位置，隨時可以查證。

原則是：自動判斷只能往安全的方向錯（不寫、告警），而且答案本身就是證據。

設計取捨與延伸

Q39題目裡你覺得不合理、或做得不一樣的地方？

五個。第一，題目是寫入後才做筆數檢查，我改成先稽核再寫入，失敗時正式表完全沒被污染。第二，寫入後的對帳失敗要自動撤銷，不能只告警：DAG 紅燈時，讀的人不該已經拿到壞的合併表。第三，交易日不能只靠行事曆，颱風假只能從「資料沒來」反推，再問交易所自己的盤中統計確認。第四，連續性檢查比筆數檢查更能抓錯。第五，staging parquet 定位成被稽核的對象，對外只開放 Iceberg。

這五點都寫在 README §8，題目明確要求「直接提出並說明理由」。

Q40資料量變成一千倍，要改什麼？

儲存與 catalog 換成 S3 和多 writer 的 catalog，查詢用 Trino 或 Spark，這套我已經在 docker 裡跑通。partition 用 evolution 改按年並排程 compaction，實測讀全部從 531 ms 降到 10 ms。擷取如果變成逐筆成交，要平行化，寫入改用 Spark 或 Flink。DAG 結構和稽核邏輯不用變。

現在的設計把「在哪裡存」「用什麼查」都留在設定裡，擴充是換元件，不是重寫。

Q41為什麼不用 LLM 判斷颱風假？

考慮過、也做過一版，收斂時拿掉。LLM 加 web search 讀新聞和公告，非確定性、要 API key、有成本，還可能被網頁內容誤導；它最多只能告訴我「新聞說停班」。人事行政總處公布的是台北市停班停課，不等於證交所休市。直接問交易所「那天有沒有成交」最準：MI_5MINS 是同一個資料源、結果確定、免金鑰，回應本身就能存成證據。

原則是：能用確定性的一手資料回答，就不用機率性的二手推論。LLM 適合讀格式不固定的內容，這裡沒有這種需要。

Q42這條管線最大的弱點是什麼？

我會說三個：對帳失敗雖然會自動撤銷，但 commit 到撤銷之間讀得到；snapshot 還沒有保留政策；證交所事後修正不會被自動發現，要手動重跑。三個都有明確的改進方向：Iceberg branch 做 WAP、訂保留期並打 tag、T+1 自動重抓比對。

完整清單在本手冊 12。回答時挑跟對方關心的面向最相關的講。

Q43為什麼合併表用 LEFT JOIN？沒有法人資料的填 0 不會誤導嗎？

T86 只列有法人交易的股票，inner join 會丟掉股票。LEFT JOIN 從行情出發，筆數永遠等於行情。填 0 的同時有 institutional_reported 欄位標記，策略可以區分「法人真的零交易」和「這檔沒有出現在 T86」。

寫入後對帳兩條：合併表筆數等於行情筆數；有法人資料的列數等於法人筆數。

Q44如果你加入一家還在手動下載的公司，怎麼讓大家信任自動化？

平行比對。新管線上線後和手動下載同時跑兩週，每天比對，差異逐筆解釋。同時讓訊號報告附上資料版本號，讓「哪一版資料」變成可以查證的事實。信任建立後，再由主管拍板停用手動流程。

這是報告第 4 頁落地計畫的核心。

還原權值與公司行動

Q45公司行動不在題目範圍，為什麼要做？

兩個原因。第一，擋寫入的連續性檢查需要它：事件生效日的漲跌是相對開盤競價基準，不是昨收。10/23 颱風日除息的 2028、6931 在 10/27 生效，沒有事件表，這兩檔會讓檢查失敗、整天擋下。第二，策略團隊算報酬需要調整因子。所以留下來，但收窄到只用證交所公布的值：三張報表、因子 = 參考價 ÷ 事件前收盤、還原價查詢時才算。

加東西要有理由，也要有邊界：不抓明細頁重算、不接第三方、不做人工審核流程。

Q46為什麼不直接買現成的還原價？

現成的還原價是黑盒，資料源算錯時我們無從得知，也多一個外部依賴。證交所公布的參考價就是市場交易的基準，因子 = 參考價 ÷ 事件前收盤，直接從源頭取；原始回應存在 Bronze，每個因子都查得到出處，也都過了讀取檢查。

曾經用 FinMind 做第三方交叉比對，收斂時拿掉：參考價是證交所定義的，第三方的值只是轉述，多一個依賴換不到新的資訊。

Q47調整因子怎麼驗證？為什麼誤差是「捨去到分」？

驗的是我們讀對沒有。四條：因子在合理範圍，除權息 (0, 1]、減資和分割 (0, 100]，超出就擋；非 X 日收盤減漲跌要等於開盤競價基準，也擋；TWT49U 同一列裡，前收減權值+息值、捨去到分要等於參考價；事件前收要等於我們自己 Silver 的前一日收盤，這兩條告警。錄到的 94 筆除權息全部成立，參考價差 1 分也抓得到。

容忍度要從資料怎麼產生推出來：證交所是捨去到分（2330 那一列 1,845 − 6.000035 = 1,838.999965，公布 1,838.99），所以條件是 0 ≤ 差 < 0.01，用 decimal 精確計算。「誤差一檔」在千元以上是 5 元，太鬆。

Q48為什麼不從明細頁用官方公式驗算參考價？

做過，收斂時拿掉。參考價是證交所自己的定義，市場就照它交易；就算公式算出來不同，生效的還是公布值。所以要驗的是「我們讀對沒有」，不是「證交所算得對不對」。公式驗算要每筆事件多抓明細頁，還要處理現金增資、捨去這些細節，複雜度高、價值低。同一列三個欄位互相勾稽，加上交易所自己的價格序列（收盤減漲跌等於開盤基準），就能抓到讀錯欄和解析錯誤。

驗證要對準會出錯的地方，也就是我們的解析。驗算別人的定義，對不上時也只能照公布值用。

Q49為什麼存原始價加因子，不存調整後的價格？

調整後價格每次除權息都要改寫整段歷史，舊 snapshot 全部和今天對不上，「上週訊號用哪一版」就答不出來。存原始價和每日因子，任何一個版本都能在查詢時算出當時的還原價；因子錯了也只改一筆。

這是把事實（證交所印的價格）和衍生值（還原價）分開存。

Q50前復權和後復權，回測該用哪個？

報酬率兩者一樣。拿價格水準做特徵時用後復權：第一天固定、往後調整，新的一天加進來不會改變過去的數字。前復權用之後的因子調整過去，價格水準含有未來資訊。

例如「突破 100 元」這種條件，在前復權下會因為之後的除息而改變。

Q51還原股價用 DuckDB 的 view 不行嗎？

兩個問題。第一，DuckDB 的 Iceberg extension 能接 REST catalog、S3 Tables 和（實驗中的）Glue，接不到我們的 SQL catalog。第二，更根本的是固定的前復權 view 本身帶 look-ahead：未來一有除權息，過去的價格水準就全部改變。point-in-time 的只有後復權，或帶 as-of 參數的計算。給 SQL 使用者的話，Trino view 用 exp(sum(ln(adj_factor))) over (partition by stock_id order by trade_date) 累乘做後復權就好。

還原價是衍生值，用 view 或查詢時算都可以；重點是方向：後復權加進新的一天，舊的數字不會變。

Q52公司行動的檢查對不上，為什麼只告警、不擋住整天？

公司行動是加值欄位；行情和法人才是策略團隊明天一定要用的。兩條交叉比對對不上時，照證交所公布值入庫並告警，讓人去看，不讓 1,390 檔都延遲。因子超出範圍不一樣，那是確定的解析錯誤，所以擋。

擋或不擋看兩種代價：每天誤擋的檢查會讓人開始忽略告警，而證交所公布值本來就是生效的值。

Q53有疑問的公司行動，為什麼不讓交易員審核？

做過一版，收斂時拿掉。它要另一個 DAG、Airflow 的表單、只新增的審核紀錄表和具名登入，遠超過題目範圍。收斂後也沒有需要人裁決的「多方對不上」：只用證交所公布值，它就是生效的值；我們的檢查只驗讀取，對不上多半是解析問題，該修程式再重跑，而不是讓人填一個數字。所以現在是告警，由工程師看。

人工流程要放在真的需要判斷的地方。真的要做時，紀錄要只新增不修改，「誰、何時」取自登入身分，不能自己填。

上雲與運算引擎

Q54之後要大量 GPU 訓練，Polars、Spark、Trino、DuckDB 選哪個？

Polars 為主。日頻 20 年才 700 萬列，單機就裝得下，瓶頸在 GPU 訓練不在資料處理；Polars 有 GPU 引擎，和 PyTorch、XGBoost 之間走 Arrow，少一次複製；清洗也已經用 Polars，研究和 production 算法一致。Trino 是給人查資料的 SQL 服務，AWS 上換 Athena；Spark 留給逐筆成交這種單機放不下的量；DuckDB 當 notebook 裡的 SQL 工具。

選引擎看資料量和瓶頸在哪，不看名氣。

Q55基因演算法挖因子，運算怎麼安排？

瓶頸是同時評估上萬個候選公式。把價格、成交量整理成「日期 × 股票」的 GPU 張量，候選公式用 PyTorch 運算批次評估，Rank IC 也在 GPU 上算，資料只搬一次。訓練資料用指定的 Iceberg snapshot 讀取，結果可以重現。

這一段 DataFrame 引擎反而慢，因為每個公式都是一次完整的面板運算。

Q56搬到 AWS（S3＋Glue），程式要改哪些？

大部分是設定：catalog 類型、warehouse、資料路徑三個環境變數，加上 Glue 和 S3 的套件；告警改送 SNS 或 Slack；登入換 MWAA 的 IAM／SSO。清洗、稽核、對帳與撤銷、還原價、Iceberg 讀寫和 DAG 都不用改。

S3＋Postgres catalog 已經在 docker 裡不改程式跑通；Bronze 寫 S3 是設計上支援，還沒實測，要照實說。

Q57AWS 上用 MWAA 要注意什麼？

版本：本專案在 Airflow 3.3 開發，要確認 MWAA 提供的版本，CI 的 DAG 測試也改用同版本的 image。部署：CD 的 deploy-aws job 用 OIDC 把同一包 bundle 同步到 MWAA 的 S3。查詢：Trino 換 Athena，接同一個 Glue catalog。

這些都在設定或部署層，pipeline 本身不用改。
